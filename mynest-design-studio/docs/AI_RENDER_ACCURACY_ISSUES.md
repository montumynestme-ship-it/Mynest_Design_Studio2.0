# MyNest Design Studio — 3D / AI Render Accuracy Issue Register

**Purpose:** Track and resolve why AI-generated room renders can look attractive yet fail to reproduce the canonical 2D design and deterministic 3D base render. This is an investigation-and-fix register, not a claim that every listed defect has already been reproduced in the current runtime.

**Priority invariant:** The canonical 2D design and its immutable design-version snapshot are authoritative. The deterministic 3D scene/base render is the geometry reference. AI may change visual appearance only; it must not redefine furniture inventory, identity, count, position, dimensions, rotation, room assignment, walls, room boundaries, doors, or windows.

**Evidence labels**
- **Observed in supplied screenshots:** visible in the six-room AI Render gallery screenshots. Screenshot-level observations are useful triage evidence but do not prove exact transform errors.
- **Historical report:** stated in previous project audit/report material; re-check against current source and exact artifacts before treating as current.
- **Needs verification:** plausible failure mode or inconsistent documentation that requires a reproducible test.
- **Verified current behavior:** only use after the implementation agent inspects current source, traces the runtime request, and captures test evidence.

## 2. Issue register

Status at document creation is deliberately conservative. The implementation agent must update each status with source paths, test names, artifact IDs/hashes, and a short evidence note.

### AIR-01 — AI output changes furniture inventory or arrangement

- **Priority:** P0 / critical invariant
- **Evidence:** Historical report described furniture identity/count/arrangement drift in an instruction-edit path. One historical sample reportedly identified 4/5 items in a Kontext output and 5/5 in a Canny-conditioned output; this is sample-specific and not a production-wide result.
- **Failure modes:** missing or extra furniture; duplicate objects; object identity/type changes; shifted, resized, rotated, or merged items; invented decor interpreted as canonical inventory.
- **Investigate:** actual provider/model and request body; whether the selected path consumes the deterministic base image or a structural control image; prompt and negative constraints; inventory and geometry validators; output status handling.
- **Required fix principle:** Do not assume prompt wording alone can guarantee geometry. Prefer the smallest verified structural constraint or safe rejection/fallback. Do not change provider defaults or enable paid inference as part of this task without explicit approval.
- **Acceptance:** controlled offline tests demonstrate that a drifted/extra/missing-object fixture cannot be reported as `FAITHFUL`; uncertain cases remain `UNVERIFIED`/`NOT_ASSESSABLE`. Canonical data is unchanged by generation.

### AIR-02 — Deterministic base render crops or occludes canonical objects

- **Priority:** P0
- **Evidence:** Historical report described camera framing/occlusion problems, including a dining camera facing partitions and furniture obscured by other geometry. The supplied screenshots show varying camera framing; exact defects are not proven from screenshots alone.
- **Failure modes:** furniture lies outside the camera frustum; walls/partitions occlude key items; the base image crops doors/windows; overly wide floor space or close-up framing prevents meaningful AI conditioning.
- **Investigate:** `BaseRenderBatch.tsx`, `RoomScene3D.tsx`, `aiCamera.ts`, camera target/position/FOV, room bounds, visibility, wall clipping, and exact base PNGs from the same generation.
- **Required fix principle:** Fix the deterministic base/camera only when a reproducible defect is established. Do not add room-specific coordinate offsets to hide a general camera or bounds defect.
- **Acceptance:** fixture-driven tests or capture evidence show every expected visible object is in-frame or explicitly marked occluded/not assessable; camera output is deterministic for a fixed design version.

### AIR-03 — Open-plan room grouping and furniture assignment are inconsistent

- **Priority:** P0
- **Evidence:** Historical report described overlapping kitchen, kitchen/dining, and dining room entities and possible furniture assigned to an uncaptured composite room. Project documentation elsewhere says open-plan spaces are merged gracefully; reconcile this conflict.
- **Failure modes:** items are assigned to a room that is never captured; an item appears in two room renders; Kitchen/Dining objects disappear from the expected render; room labels and capture keys do not match canonical room IDs.
- **Investigate:** canonical item UID → room assignment → reconstructed room IDs → room eligibility/capture keys → base-render artifact inventory. Include the kitchen/dining screenshots but do not infer exact assignment from pixels alone.
- **Required fix principle:** Do not merge rooms or force uncertain assignments just to make tests pass. Preserve explicit `UNCERTAIN`/review states where evidence is insufficient.
- **Acceptance:** deterministic tests cover open-plan and separate-room examples; every canonical item has a traceable room/capture disposition, with no silent drops or duplicates.

### AIR-04 — Wall, door, and window geometry/association is wrong or unverified

- **Priority:** P0
- **Evidence:** Historical report stated that 11/13 openings associated with wall centerlines in one sample, with two missing wall IDs. This is a historical sample, not proof of the current design's status.
- **Failure modes:** opening missing, duplicated, flipped, shifted, attached to the wrong wall, or absent from the base render; uncertain opening forced onto an arbitrary wall.
- **Investigate:** opening extraction and `opening_placements`, supporting-wall selection, wall projection and orientation functions, scene construction, renderer visibility, and exact canonical/source-plan fixture.
- **Required fix principle:** Never force an uncertain door/window placement to pass validation. Keep confidence and failure reason explicit.
- **Acceptance:** frozen fixtures verify opening count, identity, orientation, wall association, and render visibility where assessable; ambiguous associations remain flagged rather than fabricated.

### AIR-05 — 2D-to-3D coordinates, dimensions, scale, or rotation diverge

- **Priority:** P0
- **Evidence:** Prior project context recorded potentially different frontend/backend meters-per-pixel defaults and calibration paths. The current checkout and formulas must be rechecked; this is not yet a confirmed current defect.
- **Failure modes:** furniture appears at a wrong scale or position; rotation sign/axis changes; units are mixed; room dimensions differ; a frontend calibration and backend fallback disagree.
- **Investigate:** canonical units and transforms, frontend `SCALE`/`computeMpp`, backend coordinate defaults, `scene.ts`, `furniture3d.ts`, scene serialization, and any round-trip conversions. Trace the same known fixture end to end.
- **Required fix principle:** Do not change a global scale or coordinate formula based only on visual impression. Identify the specific boundary and prove the conversion with known dimensions and transforms.
- **Acceptance:** tests compare canonical and scene-space positions/dimensions/rotations with documented tolerances and units; no unrelated coordinate-system refactor.

### AIR-06 — AI provider/conditioning path differs from what documentation or UI implies

- **Priority:** P0
- **Evidence:** Historical documents conflict about whether fal Kontext, single-pass Canny, or a Depth→Canny two-pass chain is active. Prior source review reported defaults of `DEFAULT_AI_PROVIDER=nvidia`, `FAL_IMAGE_MODEL=fal-ai/flux-kontext/dev`, and `FAL_USE_CONTROLNET=false`; re-verify in the current checkout before acting.
- **Failure modes:** UI/documentation claims structural conditioning while the actual provider uses text-to-image or edit-only inference; base render is not sent to the provider; flags select an unexpected model path; output is described as geometry locked without evidence.
- **Investigate:** config defaults and environment overrides (do not print secrets), adapter `supports_control_image`, actual request-body builder, registry/dispatch, `generation_service.py`, diagnostics, and request metadata. No external AI calls are required for this inspection.
- **Required fix principle:** Correct the actual path or its description with the smallest safe change. Do not change provider defaults, turn on paid API use, or enable a new conditioning pipeline without separate approval.
- **Acceptance:** offline unit tests prove each configuration selects the expected adapter/body and clearly indicates whether a base/control image is consumed. Documentation matches current code and effective deployment configuration is not guessed.

### AIR-07 — AI geometry status can claim “faithful” without output-level evidence

- **Priority:** P0
- **Evidence:** Prior audit material described both an older false-pass badge and a later tri-state correction. Current source/UI behavior must be verified. Image decode success, nonblank pixels, aspect-ratio match, or valid input does not establish object-level fidelity.
- **Failure modes:** green “Geometry Faithful” badge derived from input validity; detector uncertainty treated as pass; API status and gallery badge disagree; no verifier still becomes `FAITHFUL`.
- **Investigate:** `assess_ai_output_geometry`, `assess_ai_render`, generation-service callers, response schemas, status mapping, gallery badges, and all relevant tests.
- **Required fix principle:** `FAITHFUL` requires independent output-level evidence. Keep `FAIL`, `UNVERIFIED`, `NOT_ASSESSABLE`, and detector uncertainty distinct. Do not weaken thresholds to increase pass rates.
- **Acceptance:** regression tests prove no input-only check can produce `FAITHFUL`; uncalibrated detectors cannot silently pass; frontend displays the backend status faithfully.

### AIR-08 — Base/output render provenance is incomplete or mismatched

- **Priority:** P1
- **Evidence:** Historical reports disagree about whether production base renders and metadata are persisted consistently. Previous audit material noted that some expected base/output pairs were unavailable for audit.
- **Failure modes:** output is compared to a different base image/design version; missing request ID, model, config, seed, prompt, dimensions, or image hash; ephemeral base image makes a failure unreproducible.
- **Investigate:** generation records/storage paths, base-render persistence, design version IDs, request/response metadata, content hashes, timestamps, and gallery source selection. Never expose API keys or private URLs in logs.
- **Required fix principle:** Preserve current data contracts and avoid broad storage migrations. Add only the smallest provenance fields/persistence change justified by a demonstrated audit gap and approved scope.
- **Acceptance:** a generated artifact can be traced to the exact design version, base image hash, provider/model/config, request identifier, and output hash, or the missing fields are explicitly reported as unavailable.

### AIR-09 — Gallery compares unlike camera views or the wrong design snapshot

- **Priority:** P1
- **Evidence:** Supplied screenshots show side-by-side 2D and AI images with different projections, so pixel-level or exact transform comparison is not reliable without normalization. Historical audit material also reported a gallery snapshot-binding issue; a later source review reported that version-specific loading may already be implemented.
- **Failure modes:** current live scene shown beside an older generation; false missing-object verdict due to occlusion/crop; raw pixel difference used despite different camera framing; perspective mistaken for transform drift.
- **Investigate:** `GenerationGallery.tsx`, `scene.ts`, `design_version_id`, camera metadata, and base/output provenance. Verify existing version binding before editing; do not duplicate a fix already present.
- **Required fix principle:** Compare the exact generation snapshot and use camera-aware/structure-aware review. When comparability is insufficient, return `NOT_ASSESSABLE` instead of invented transform deltas.
- **Acceptance:** regression test confirms the generation uses its own immutable version; comparisons record camera comparability and distinguish missing, occluded, merged, cropped, and ambiguous objects.

### AIR-10 — Tests rely on mutable live data or lack reproducible fixtures

- **Priority:** P1
- **Evidence:** Historical reports cite inconsistent test summaries and failures apparently tied to mutable live plan data, opening counts, or database configuration. Those historical test counts are not current test results.
- **Failure modes:** test passes/fails depending on current database contents; expected object counts drift; a missing database URL masks test assertions; a mock test is mistaken for production fidelity proof.
- **Investigate:** existing fixtures, `frozen_v31`/canonical fixtures, database setup, test markers, and exact commands/exit codes. Keep contract tests distinct from legacy/synthetic tests.
- **Required fix principle:** Use frozen fixtures and deterministic offline tests. Do not weaken assertions, rewrite expected values just to pass, or connect to production/live databases.
- **Acceptance:** focused unit tests run without paid AI/API calls and identify database-dependent tests separately; test output and limitations are recorded accurately.

### AIR-11 — Deterministic base scene is too sparse or semantically inaccurate for faithful AI styling

- **Priority:** P1
- **Evidence:** The six supplied screenshots show that some AI outputs look photorealistic while the deterministic 3D preview and floor-plan symbols have different visual detail levels. The screenshots alone cannot tell whether an object is genuinely missing, hidden, or represented differently in 3D.
- **Failure modes:** canonical furniture exists in 2D but has no 3D representation; a furniture type maps to the wrong procedural model; doors/windows/fixtures are absent from the base image; AI fills blank areas by inventing décor.
- **Investigate:** canonical item types and IDs, 2D→3D model mapping, procedural furniture models, room-scene inventory, base PNGs, and per-item visibility. Compare inventory before blaming the AI adapter.
- **Required fix principle:** Improve or correct deterministic 3D representation only where canonical item mapping is demonstrably wrong or absent. Do not add invented objects to make the output more decorative.
- **Acceptance:** a fixture's canonical item inventory maps to explicit 3D object IDs/models or a documented unsupported/not-assessable state; base render is checked before AI generation.

### AIR-12 — Photorealism objective conflicts with geometry preservation

- **Priority:** P1
- **Evidence:** Screenshot-level review shows varied output quality: some images are highly realistic, while others are sparse or stylized. This is a quality observation, not evidence that a specific model parameter is the root cause.
- **Failure modes:** stronger restyling changes object silhouettes or adds furniture; conservative conditioning preserves edges but produces clay-like materials; prompt tweaks hide rather than solve base-scene or conditioning defects.
- **Investigate:** base render quality, provider capabilities, prompt constraints, control strength/init settings, and visual review results for exact paired artifacts. Separate geometry accuracy from material/lighting quality metrics.
- **Required fix principle:** Optimize appearance only within the canonical constraints. Do not trade geometry fidelity for visual appeal, and do not claim a prompt alone guarantees preservation.
- **Acceptance:** report two independent scores: (1) geometry/inventory fidelity and (2) appearance/material quality. A visually beautiful render that fails geometry criteria is rejected or marked `FAIL`; a visually weak but geometrically assessable render is not mislabeled as a geometry failure.

## 3. Required investigation sequence

1. **Freeze the baseline:** record Git branch/HEAD/status and preserve pre-existing edits. Identify the actual project root. Do not reset, checkout, clean, normalize line endings, or overwrite user changes.
2. **Read context first:** `README.md`, `PROJECT_CONTEXT.md`, `docs/CORE_PIPELINE_DOCUMENTATION.md`, `docs/PIPELINE_AUDIT_REPORT.md`, `docs/BASE_RENDER_FIX_REPORT.md`, and `docs/AI_RENDER_FIX_REPORT.md` when present.
3. **Verify runtime truth:** trace canonical version → room assignment → deterministic scene → base-render capture → provider dispatch/request body → AI output → validators/status → gallery snapshot. Use source and offline tests; do not invoke paid AI endpoints.
4. **Create a per-room inventory matrix:** canonical item ID/type/count/room/transform; 3D object/model; visible in base?; visible in AI output?; confidence/status; artifact IDs/hashes. Use all six supplied rooms if exact paired artifacts are available.
5. **Classify evidence before changing code:** reproduce each issue; identify root cause and owning module; distinguish confirmed defect from hypothesis. If the correct fixture/artifacts are unavailable, mark `BLOCKED`/`NOT_ASSESSABLE` and do not guess.
6. **Fix upstream first:** canonical data and room assignment → deterministic 3D mapping → base camera/capture → provider conditioning → output validation/status → gallery/provenance. AI cannot preserve information missing from its base image.
7. **Implement minimally:** one issue at a time, smallest safe diff, backward-compatible behavior, no unrelated refactors or new dependencies without approval.
8. **Test each fix:** add a regression test that fails before the fix and passes after it. Run focused offline tests, then relevant broader suites. Keep contract-valid, legacy, synthetic, and database-dependent results separated.
9. **Review visually with paired evidence:** exact same design version, room, base image, AI output, model/config/seed, hashes, and camera-comparability assessment. Do not claim precise transforms when views cannot be aligned.
10. **Update this register:** each issue must end as `FIXED_AND_VERIFIED`, `PARTIALLY_FIXED`, `NOT_REPRODUCIBLE`, `BLOCKED`, or `DEFERRED_WITH_REASON`, with changed files and evidence.

## 4. Global acceptance criteria

- Canonical 2D design and saved design versions remain unchanged by AI generation.
- No unapproved furniture is added, removed, duplicated, retyped, moved, resized, rotated, or reassigned.
- Walls, room boundaries, doors, and windows are preserved; uncertain associations are not forced.
- Every output fidelity claim is evidence-backed. `UNVERIFIED`/`NOT_ASSESSABLE` is acceptable when evidence is insufficient.
- The exact generation snapshot is used for review; base/output provenance is available or its absence is reported.
- Deterministic rendering remains the trusted fallback when AI generation or validation fails.
- No paid AI/API calls, production changes, deployments, destructive actions, provider-default changes, or new dependencies without explicit approval.
- Tests are not weakened to manufacture a pass. Report exact commands, counts, failures, environmental blockers, and limitations.
